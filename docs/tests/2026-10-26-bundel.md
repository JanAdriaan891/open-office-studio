## Per route: gemeten in de browser

Koude lading: nieuw profiel per scenario, eerst de startpagina, daarna één klik. Warme lading:
dezelfde browser, pagina opnieuw geladen en dezelfde klik. Statische server zonder compressie:
gehashte `assets/` krijgen `immutable`, de rest krijgt `no-cache` met ETag. De bytes zijn de
werkelijk opgevraagde bestanden, opgezocht in de bestandstabel hierboven. gzip en Brotli zijn dus
wat een comprimerende server zou versturen. Een warme lading verstuurt bijna niets: alles komt uit
de cache of krijgt een 304.

Tijd = mediaan van drie koude rondes, van klik (of navigatiestart) tot het laatste afgeronde
netwerkverzoek, met de editor zichtbaar (“Editor laden…” weg). Schermafbeeldingen in
`.local/bundelmeting/scherm-*.png` bevestigen dat iedere editor echt geopend was. PSS =
proportioneel geheugen van alle Chromium-processen samen, piek tijdens de stap. Een lege browser
gebruikt al 319–383 MiB.

## Browserroute tegenover de serverroute

Als servergebaseerde referentie dient de kantoorruntime zelf: LibreOffice 24.2.7.2 headless.
Gemeten is één conversie per proces (`--convert-to`), met `/usr/bin/time` voor tijd en piek-RSS.
“Koud” betekent een nieuw gebruikersprofiel, inclusief het aanmaken daarvan. “Warm” betekent een
hergebruikt profiel, mediaan van drie.

| Conversie (eigen voorbeelden) | Koud (s) | Piek-RSS koud (MiB) | Warm, mediaan (s) | Piek-RSS warm (MiB) | Fouten |
|---|---:|---:|---:|---:|---:|
| DOCX → ODT | 2,47 | 224 | 2,29 | 224 | 0 |
| DOCX → PDF | 2,14 | 220 | 1,97 | 220 | 0 |
| XLSX → ODS | 2,07 | 221 | 1,99 | 220 | 0 |
| XLSX → PDF | 1,97 | 220 | 1,76 | 221 | 0 |
| PPTX → ODP | 2,84 | 240 | 2,47 | 240 | 0 |
| PPTX → PDF | 2,77 | 225 | 2,59 | 225 | 0 |

Vergelijking, met de grenzen erbij:

- **Bytes naar de client**: de browserroute vraagt per editor 1,8–7,0 MiB Brotli (6,8–29 MiB
  ruw) bij de eerste keer. Een serverroute stuurt alleen een viewer/editor-UI en documentdata. Die
  hoeveelheid is **onbekend**: er is geen servergebaseerde editorsuite (zoals Collabora Online of
  OnlyOffice Docs) gemeten, en een serverimage is geen vergelijkbare browsermeting.
- **Tijd per handeling**: de engine opent een document in de browser in 0,4–1,7 s koud (Tekst met
  voorbeeld 4–8 s) en in Node in 50–250 ms. De headless runtime heeft 2–3 s per conversie nodig,
  omdat elke conversie een nieuw proces start. Een permanent draaiende server is sneller. Dat is
  **niet gemeten**.
- **Geheugen**: de browserroute gebruikt piek 510–650 MiB PSS voor de hele browser (de lege
  browser zit al op 320–380 MiB). De runtime gebruikt per conversieproces 220–240 MiB RSS.
  Geheugen per gelijktijdige gebruiker op een server is **onbekend**.
- Netwerklatentie, gelijktijdige gebruikers, samenwerking en bewerken in de serversuite zelf zijn
  **niet gemeten**.

## Niet gemeten

- **Laadtijd en geheugen in Firefox, Safari en de Tauri-webviews** (WebKitGTK, WebView2,
  WKWebView). Procedure: dezelfde build in `.local/bundelmeting/dist` serveren, dezelfde tien
  scenario's draaien en per scenario drie keer koud (nieuw profiel) en drie keer warm meten. Leg
  browserversie, CPU, RAM en energiestand vast. Voor de webviews: devtools-netwerkpaneel of
  `WEBKIT_INSPECTOR_SERVER`, geheugen via de procesboom (PSS).
- **Laadtijd over een echt netwerk**: hier was alles lokaal, zonder latentie. Herhaal met
  netwerkvertraging (bijvoorbeeld CDP `Network.emulateNetworkConditions`, 40 Mbit/s en 40 ms RTT)
  en met een server die echt Brotli/gzip uitlevert.
- **Grote-bestandproef** in de browser (bijvoorbeeld de corpusbestanden met tijdslimiet uit het
  verslag van 21 oktober).
- **Servergebaseerde editorsuite** (bytes naar de client, geheugen per gebruiker, latentie bij bewerken).
- **Rustige machine**: herhaal de tijden zonder parallelle builds, met een vaste CPU-governor.

## Herhalen

```bash
node scripts/meet-bundel.mjs                     # build + bytes + manifestroutes + Node-engines
node scripts/meet-bundel.mjs --geen-build --browser=/pad/naar/chrome --herhaal=3
node scripts/meet-bundel.mjs --geen-build --geen-engines --server   # serverroute + ODF-1
node scripts/praktijkcorpus.mjs [--proef]
```

`--database-bestand=<pad>` kiest het MDB-bestand voor het databasescenario. Standaard is dat het
eerste `.mdb` uit `.local/corpus/bestanden` (hier `jackcess-07583f9a…mdb`, 139.264 bytes).
`--scenario=start,tekst,…` beperkt de browsermeting. Een cache op inhoudshash in
`.local/bundelmeting/compressie-cache.json` voorkomt dat ongewijzigde fonts en WASM opnieuw met
Brotli-11 worden gecomprimeerd.
